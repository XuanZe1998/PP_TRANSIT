# 三个应用共用服务器的部署方案

制定日期：2026-10-11。目标服务器：server-207，207.57.122.109。

本方案覆盖 Linknux/API 中转站、Halo 社区版博客、家庭点餐小程序后台。属于部署设计，尚未执行服务器安装、重启、DNS 切换或数据迁移。

## 本期范围（2026-10-11 用户确认）

- 本期部署当前项目与 Halo；家庭点餐后台暂不部署，不创建对应服务或业务数据库。
- 博客域名确定为 `blog.linknux.com`；点餐域名改为 `food.linknux.com`，保留供后续启用。
- 三个系统均无旧数据，按全新安装设计，不需要迁移旧数据库或上传文件。
- 微信 AppID/AppSecret 已准备好，本期无需读取或注入 AppSecret。
- 本机 DNS 查询已确认 `linknux.com`、`api.linknux.com`、`blog.linknux.com`、`food.linknux.com` 的 A 记录均指向 `207.57.122.109`。这仅验证解析，不表示服务已上线。
- 备份位置确定为服务器 `/var/backups/linknux/` 与本机 `D:\Backups\server-207\`。D 盘实测可用约 359 GiB，备份放在项目仓库外。
- 用户已指定采用当前工作区版本，先完成验证并整理为可发布版本。本次首次安装采用本地 Git 发布快照追溯来源；保留用户当前分支和工作区，不自动推送远端或触发 master 的自动部署。常规 master 增量发布流程保持原有约束。

后文保留家庭点餐的后续接入设计；涉及该应用的部署和验收步骤在本期跳过。

## 1. 结论与适用范围

建议先在现有服务器部署三个系统：Nginx 统一提供 HTTPS，三个 Java 应用分别由 systemd 管理，共用一个 MySQL 实例、使用独立数据库和独立账号；Redis 只供 API 中转站使用。

家庭点餐项目已检查，路径为 `D:\Code\OutSource\点餐小程序`。它是微信原生 TypeScript 小程序 + Java 17/Spring Boot + MySQL，供家庭成员点选菜品，没有支付、售卖、配送，当前代码不依赖 Redis。小程序客户端通过微信开发者工具上传，不需要在 VPS 上运行 Node.js 前端服务。

4 vCPU / 8 GB 内存足以作为低访问量中转站、个人博客和家庭点餐的起步配置。该判断基于机器实测和代码依赖，不代表已通过业务压测。中转业务增长时优先增加资源或拆分中转服务。

## 3. 域名、入口与运行方式

下列域名已由用户确认并核对 A 记录；`food.linknux.com` 本期只保留解析，后续再配置后台与 HTTPS 服务。

| 系统 | 对外域名 | 本机服务 | 运行方式 |
|---|---|---|---|
| Linknux 前端 | linknux.com | Nginx 静态文件 | Vue 构建产物 |
| Linknux API | api.linknux.com | 127.0.0.1:8089 | Java 17 + api-transit.service |
| Halo | blog.linknux.com | 127.0.0.1:8090 | Java 21 + halo.service |
| 家庭点餐后台（后续） | food.linknux.com | 127.0.0.1:8080 | Java 17 + family-order.service，本期不安装 |
| MySQL | 无公网域名 | 127.0.0.1:3306 | 一个 MySQL 实例 |
| Redis | 无公网域名 | 127.0.0.1:6379 | 一个 Redis 实例 |

只对外提供 HTTP/HTTPS，SSH 为管理入口；三个应用端口、数据库和 Redis 均绑定回环地址。防火墙同时覆盖 IPv4/IPv6。证书自动续期，并测试续期流程。

选择 systemd 是为了沿用中转站现有发布、健康检查和回滚流程，并让两个 Java 17 应用共享安装好的 JRE。Halo 官方支持 JAR + systemd 部署；为 Halo 指定独立的 Java 21 绝对路径，避免更换系统默认 Java 影响原项目。

Halo 使用独立子域名，官方不支持挂在 `/blog` 子目录。其对外地址设置为 `https://blog.linknux.com`。社区版运行包来自官方发布渠道，固定经验证的具体版本和校验值；不使用付费版示例包替代社区版。

若以后改用 Docker，需要一起调整中转站发布流程和数据库访问方式。家庭点餐现有 `deploy/compose.yml` 会另起 MySQL；本方案不直接执行该文件，以免形成重复数据库实例。

## 4. 初始资源分配

以下是上线初始配置候选值，须通过启动、上传和联合运行验证，不是实测消耗。MemoryMax 指整个进程及其计入 cgroup 的内存上限，不能等同于 Java 堆。

| 组件 | 初始配置 | 服务内存预算/上限 |
|---|---|---:|
| API 中转站 | 沿用 -Xms512m -Xmx2g | 3072 MiB |
| Halo | -Xms256m -Xmx512m | 1024 MiB |
| 家庭点餐（后续） | -Xms128m -Xmx384m，本期不启动 | 768 MiB，后续预算 |
| MySQL | InnoDB buffer pool 从 384 MiB 起，连接上限约 80 | 1280 MiB 预算 |
| Redis | maxmemory 从 96 MiB 起，保留持久化/重写余量 | 192 MiB 预算 |
| 系统、Nginx、采集与备份 | 预留 | 约 768 MiB |
| 本期未分配余量 | 不启动家庭点餐，按实际总内存计算 | 约 1.6 GiB |

本期四个主要组件合计约 5.44 GiB；后续增加家庭点餐后合计约 6.19 GiB。平时应低于上限并争取保持 MemAvailable ≥ 1 GiB。MySQL/Redis 的硬上限需测过数据库峰值、备份和重写后再配置，不能只依据该表直接限制进程。

中转站现有 2 GB 堆设置保留；如果发生 OOM 或持续内存压力，应降低功能并发或升级内存，不能仅提高各服务上限。点餐图片上传会解码和重新编码图片，需特别测试最大允许尺寸和连续上传；必要时限制上传并发。

使用 CPUWeight 设置共享调度优先级：中转站和数据库较高，家庭点餐中等，Halo 和备份较低；初期不把四个 vCPU 固定分区。备份和构建避开活跃时段。代码构建、前端构建均在本机或 CI 完成。

增加约 4 GiB Swap 作为异常峰值缓冲，部署时监测换入换出；Swap 不能替代物理内存，持续交换即需要处理容量问题。

## 5. 数据库、账号和配置

使用 MySQL 8.4 LTS 的已发布维护版本，安装时记录实际版本。家庭点餐 Compose 已指定 8.4，但其 README 记录的实际数据库验证是 8.0.46；因此三个应用都必须在选定的 8.4 版本上验证迁移和 CRUD 后再启用正式数据。

| 数据库 | 应用账号 | 用途 |
|---|---|---|
| api_transit | api_transit_app | 中转站账户、钱包、渠道、审计等 |
| halo | halo_app | 博客内容和配置 |
| family_order | family_order_app | 家庭、用户、菜谱、点菜和会话 |

三个密码独立随机生成。应用账号只访问各自数据库，不使用 root，不具有其他数据库权限。迁移需要的建表/改表权限限于本应用库；备份使用单独账号和私有凭据文件。

数据库连接池：中转站沿用最大 20、最小 2；家庭点餐显式设最大 5、最小 1；Halo 连接池也显式设置较小上限，例如 5，参数按安装版本核对。总连接预算包含备份与管理连接。

Redis 只服务中转站：使用 ACL/密码；根据用途决定持久化与淘汰策略，禁止任意淘汰关键限流、锁和状态数据。若采用 noeviction，必须验证容量不足时应用的错误处理。钱包与订单的权威数据仍在 MySQL。

服务器配置分别放在：

- 中转站：`/etc/api-transit/application-local.yaml`，沿用已有配置位置。
- Halo：`/etc/halo/application.yaml`，显式设置数据库、工作目录、外部地址和回环监听。
- 家庭点餐：`/etc/family-order/application-prod.yml`，由启动参数显式加载，使用 prod profile。

私有文件由 root 管理，对相应服务组开放最小读取权限，不提交 Git、不装入公开发布包。微信 AppSecret 仅注入家庭点餐服务；中转站加密密钥必须备份，并在数据迁移时保持原值，否则旧的加密数据无法解密。

## 6. 文件与磁盘规划

| 内容 | 服务器路径 |
|---|---|
| 中转站版本、当前软链接 | /opt/api-transit/releases、/opt/api-transit/current |
| 中转站前端 | /var/www/linknux-releases、/var/www/linknux |
| 中转站上传等持久数据 | /var/lib/api-transit |
| Halo 版本、工作目录 | /opt/halo/releases、/var/lib/halo |
| 家庭点餐版本、图片 | /opt/family-order/releases、/var/lib/family-order/uploads |
| 服务器短期备份 | /var/backups/linknux；中转站发布前备份继续沿用 /var/backups/api-transit |
| 离机备份（Windows 本机） | D:\Backups\server-207，位于项目仓库外 |

服务使用三个独立 Linux 用户。版本目录以只读为主，上传和工作目录允许相应应用写入。点餐设置绝对 UPLOAD_DIR 和 HTTPS PUBLIC_URL；不能将容器示例的 `/app/data/uploads` 直接用于原生运行。

对根分区约 87 GB 的初始容量预算：系统与运行时 12 GB、版本包 8 GB、数据库 15 GB、上传附件 12 GB、日志 3 GB、本机备份 10 GB、Swap 约 4 GiB，剩余约 22 GB 作为增长空间。均为配额规划，不是新增分区。

保留中转站现有 5 个版本；其他应用保留最近 3 个版本。限制 Nginx、应用文件日志与 journal 总量；启用轮转和过期清理。图片增长明显时转移到对象存储，但家庭点餐当前上传实现是本地文件，转移前需要实现存储适配和访问权限验证。

## 7. 各应用上线要点

### API 中转站

- 保持 SSE 所需的关闭代理缓冲、足够代理超时和客户端断开处理；不能对流式响应使用普通短超时。
- 保持现有 OAuth 回调域名、CORS 和支付回调域名契约；迁移服务器时更新解析与相关 IP 限制。
- 本机健康检查使用 `/actuator/health`，公网继续阻止访问 `/actuator/`。
- 当前发布工具仅接受干净、已提交且与 origin/master 一致的 master。当前工作区存在未提交修改，上线版本需先确定并完成项目要求的验证。
- `deploy/server/api-transit-release` 要求现有后端/前端 current 指向有效版本，因此裸机首次安装必须有独立 bootstrap 流程：建立用户、目录、配置、数据库、首个版本和软链接；验证首次启动，再启用增量发布。
- 现有脚本可回退后端/前端软链接，但不会自动回退数据库迁移。数据库结构变化必须验证旧版兼容性，或准备维护窗口和单独的恢复步骤。

### Halo

- 采用社区版 JAR、独立 JRE 21、独立 MySQL 库和固定工作目录，启动方式依据安装版本官方文档核对。
- 生产环境使用 MySQL，不使用 H2。
- 初期安装少量必要主题/插件，附件上传限制先设为约 20 MB，后续按实际需求调整。
- 备份必须同时覆盖数据库与工作目录中的附件、主题、插件、配置。

### 家庭点餐小程序

- 使用 prod profile，保持 `app.dev-auth-enabled=false`，不部署 local H2 数据库和演示登录。
- 当前源码产物是 `family-order-1.0.0.jar`；发布时按构建结果生成版本目录，不依赖永久固定的包名。
- 通过 Flyway 自动迁移版本化 app_* 表，不手工执行旧 `database/schema.sql`。
- 微信登录依赖真实 AppSecret；上线前验证真实 code 换取身份、家庭邀请、点菜、取消、厨师完成、图片上传及重启后数据仍存在。
- 后续使用 `food.linknux.com` 同时提供 API、上传和下载；客户端配置中的本机地址必须替换，保持 mode=server。
- 在微信平台核对 request/uploadFile/downloadFile 合法域名和隐私配置，并核对当前账号上线所需信息。自用属性不能代替真实微信登录和域名联调。
- 客户端交付使用微信开发者工具；VPS 只承载后台和图片。
- 现有 HTTP smoke 脚本只允许本机开发数据，不能直接当作公网生产验收脚本执行。

## 8. 备份、监控和恢复

本期两个数据库每晚分别做一致性备份，同时备份对应上传/工作目录和必要私有配置；家庭点餐以后接入同一机制。

备份位置与同步方式已选定：

- 服务器：`/var/backups/linknux/daily/`，保留最近 3 天的日常备份；中转站原发布前备份目录保持不变。
- 本机：`D:\Backups\server-207\daily\` 与 `D:\Backups\server-207\weekly\`，分别保留最近 7 个每日备份和 4 个每周备份。
- 部署时配置服务器夜间备份任务与本机拉取任务。拉取使用校验过主机指纹的 SSH、专用受限备份账号和专用密钥，不使用保存的 root 密码，不复用发布账号权限。
- 本机任务只在电脑联网且可运行时同步；电脑离线时服务器仍产生本地备份，下次运行补拉尚在保留期内的文件。电脑离线超过 3 天可能造成中间备份缺失；离机备份超过 24 小时未更新需要提示。
- 包含数据库和私有配置的备份加密保存，恢复密钥单独保存；私有文件不进入项目仓库。同步成功并核对校验值后再执行保留清理。
- 该离机方案无需新增云存储费用，但不能保证电脑长期离线时的恢复目标。若需要全天候离机备份，应后续改用持续在线的存储目标。

上述路径和任务是部署方案，当前尚未创建备份文件或注册定时任务。

中转站如开始承载真实钱包/订单，目标 RPO 设为不超过约 1 小时：在每日全量基础上启用并验证 binlog 归档到离机存储。博客和家庭点餐可以接受约 24 小时的初始 RPO。RTO 目标约 2 小时，需通过恢复演练验证，不能把目标当作现有能力。

每次升级前备份变更应用的数据库和文件。恢复先在临时库/目录演练；恢复旧数据库会丢失备份之后的新数据，不能与应用软链接回退混为一谈。月度抽查一次恢复；至少在首次上线前完成一次完整演练。

采用轻量主机指标采集和外部可用性检查；无需在这台机器上额外运行一整套重型监控平台。建议阈值：

- 可用内存低于 1 GiB 持续 10 分钟，或任何 OOM：检查/调整服务。
- CPU 忙碌持续超过约 70%、CPU steal 持续偏高、Swap 持续换入换出：定位宿主机/应用问题。
- 根分区占用超过 70% 预警，超过 85% 优先处理；持续保留至少约 15 GB 空间。
- 检查 API 错误率与延迟、SSE 断连、数据库连接数、三个服务自动重启次数、备份与证书续期结果。

三个系统共用数据库和服务器属于单机方案，服务器或 MySQL 故障会同时影响它们；独立账号提供权限隔离，不能提供故障隔离。

## 9. 实施顺序与验收

1. **确定输入**：域名、全新安装和备份路径已确定；剩余需确定当前项目发布版本，并记录服务器地区和实际带宽。
2. **准备主机**：安排所提示的重启，安装运行时和基础组件，建立服务用户、目录、私有配置、Swap、防火墙、证书。改 SSH 策略前保留现有连接，并先验证新管理登录方式。
3. **数据库联调**：创建三个独立库和账号，在选定 MySQL 8.4 版本上验证迁移、读取和写入；验证两个 Java 17 应用及 Halo Java 21 的启动。
4. **家庭点餐上线（本期跳过）**：后续构建 JAR，配置 systemd、Nginx 和微信合法域名，完成家庭使用流程和最大图片上传真机测试。
5. **Halo 上线**：配置博客域名、数据库、目录和主题，验证文章发布、图片、登录与服务重启。
6. **中转站上线**：完成首次引导，验收前后端、OAuth、模型转发、SSE 和涉及的业务功能；如迁移数据，保留加密密钥与一致的数据快照。
7. **联合验收与备份恢复**：本期两个系统同时运行，观察至少 24～48 小时；使用可控的小流量验证转发，同时操作博客上传，确认没有 OOM、持续交换或异常延迟，并验证服务器备份、本机拉取与恢复。

编译和测试在本机/CI 执行，点餐至少运行 npm run check 和 mvn -f backend/pom.xml test；中转站运行仓库规定的后端/前端验证及分页守卫。只修改部署文档无需新增业务测试。本方案尚未执行这些发布前检查。

## 10. 扩容路径与执行前信息

家庭自用点餐不会成为主要容量来源。若中转站负载增长，先按指标确定瓶颈：内存紧张优先升级到 16 GB；API 占用 CPU/网络时将中转站迁到独立服务器；数据库成为瓶颈时再独立部署或使用托管数据库。域名、独立库和持久目录保持不变，便于迁移。

域名、无旧数据和备份路径已经确定。执行前仍需要确定当前项目的上线版本，核对 Halo 安装版本与服务器线路。微信 AppSecret 本期不使用；未来启用时与数据库密码一样，通过服务器私有配置注入，不发送到聊天中。
