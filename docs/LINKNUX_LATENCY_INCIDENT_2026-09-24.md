# Linknux 全站加载缓慢：2026-09-24 只读排查

## 结论与边界

当前执行环境访问 `linknux.com`、`api.linknux.com` 和 SSH（同一 IP `207.57.122.109`）间歇性建连超时或连接中断；服务器本地访问前端和公开 API 较快，CPU、内存、磁盘无明显压力。另一方面，两个独立的 20 节点全球探测均返回 HTTP 200。**证据指向受影响网络到入口的路径问题，不能称为全球性服务故障，也不能归因于已证实的 Vue 渲染或数据库瓶颈。**探测节点各只有一次快照，仍需从实际受影响的运营商/地区复测，不能仅靠全球探测判定所有用户正常。

目前尚未修复生产网络，不能把仓库里的前端优化或重新发布当作修复。此文不包含凭据、带鉴权的请求或运行日志。

## 已获得的基线

- 外部 `curl` 直接访问同一 IP：`/`、`/market`、`/services` 以及公开 API 多次出现 5 秒连接超时，另有 TLS 已完成但 15–30 秒未收到首字节；成功的首页请求约 1–9 秒。DNS 通常在数十毫秒，故不能只归因于 DNS。静态资源有成功请求约 1.5 秒。`--noproxy '*'` 测试仍复现。
- 外部 Chromium 冷启动一次：首页 `DOMContentLoaded` 约 22.1 秒，HTML 首字节约 18.8 秒。一次完整页面跳转 `/market`、`/services`、`/docs` 分别约 1.2、6.3、10.4 秒；同页 SPA 点击 `/market` 首次约 4.6 秒，随后 `/services` 约 1.5 秒、`/docs` 约 1.0 秒、返回已加载的 `/market` 约 0.8 秒。冷跳转涉及大量懒加载资源，热跳转显著改善；这些是样本，不是全站 SLO。
- 独立探测快照：Check-Host 报告 `4d354ab1k96b` 的 20 个节点访问首页均为 200（约 0.54–2.79 秒），报告 `4d354abfkb4d` 的另 20 个节点访问公开站点配置 API 均为 200（约 0.17–1.67 秒），DNS 指向同一 IP。另一次 TCP 443 探测 `4d356ddfkd98` 在香港、东京、新加坡、胡志明市四节点均可建连（约 8–173 ms）。各节点只有一次快照，不能推出其持续稳定。
- SSH 只读检查：负载约 0.28、可用内存约 6 GB、磁盘使用约 6%，`nginx`、`api-transit`、MySQL、Redis 均为 active。本机 `127.0.0.1:8089/public/site-config` 三次约 10–14 ms，`/public/models/summary` 三次约 624–666 ms；本机连 HTTPS 入口首页成功请求约 0.15–0.62 秒。稍后多次 5–6 秒 SSH 建连超时，无法获取可靠的网卡**增量**指标。一次读取显示 `eth0` 累计 RX dropped 863254/265536446 包、TCP 重传 72381、SYN 重传 10017、listen overflow 0；这些是自启动以来累计值，没有时间差分或对照，**不能**据此定性当前丢包位置或故障原因。
- 当前线上入口资源哈希与本地 `web/dist` 不一致。生产 Nginx 配置由独立运维维护，现有 `deploy-production.ps1` 仅发布前后端产物，不安装 Nginx 配置；因此不能通过普通应用发布来声称修复入口网络。

## 2026-09-24 补充复测（当前执行网络）

- `curl -4 --noproxy '*'` 对首页、`/market`、公开站点配置和模型摘要各测三次（连接上限 4 秒、总上限 10 秒）：**12 次中 6 次超时**。其中 5 次未完成 TCP 建连，另 1 次 API 已完成 TLS 握手却在 10 秒内未收到 HTTP 首字节。成功样本的首页约 1.39 秒，`/market` 约 1.55–2.47 秒；这说明并非每次都慢，也不能用成功均值掩盖失败率。随后首页与站点配置 API 各一次均再次 TCP 超时，SSH 亦多次超时。
- Chromium 公共导航三次冷上下文采样：第一次首页 30 秒超时；第二次首页 2.58 秒、首次 SPA `/market` 17.42 秒、`/services` 等待 30 秒超时；第三次首页 2.71 秒、首次 `/market` 6.04 秒、`/services` 1.33 秒、`/docs` 0.43 秒、热返回 `/market` 0.12 秒。另一次成功样本首页约 4.11 秒、首次 `/market` 5.79 秒、`/services` 2.33 秒、热返回 `/market` 0.12 秒。该次慢资源包括线上真实哈希的懒加载 JS（约 2.4–2.9 秒）和公开 API（约 1.4–1.8 秒），不是本地 `dist` 的文件名；每次冷上下文不等于完全相同网络条件。
- 路由切换指标测的是 URL 到目标组件可见且经过两帧，**不代表列表数据完全加载**。首页 DNS/连接/首字节/FCP 来自 Navigation/Paint Timing；接口仍需单独看 `curl` 与 Network。浏览器脚本只发起匿名公共页面访问，不存储请求头、Cookie 或查询参数。第一次本地 Vite preview 冒烟：首页约 0.37 秒、首次市场约 0.41 秒、服务约 0.11 秒、热市场约 0.10 秒；本地后端未配置，API 5xx 计数不用于生产结论，也不能把本地 `dist` 当作线上资源。
- `tracert -d` 可见中间路径，但 16–18 跳无 ICMP 响应不等于终点丢包，也不能单凭它定位运营商故障。两个此前受影响用户的运营商/地区尚未取得；目前只证明当前执行网络受影响，不能完成“两个受影响网络”的验收。

## 复测与处理

1. 优先在至少两个实际受影响的运营商/地区，并以一个正常地区作对照，在 Windows 机器上运行 `./scripts/measure-site-latency.ps1 -Runs 5 -OutputPath <本地 CSV 路径>`；同一机器分别在故障时段和正常时段运行。脚本从**线上 HTML**发现当前 JS/CSS 资源，输出 HTTP 状态、curl 退出码、目标 IP 和各阶段毫秒数。`status=0`、`curlExit=28` 是超时；`failurePhase` 根据 TCP/TLS/HTTP 阶段近似分类，失败且无 HTTP 响应时 `firstByteMs` 为空。`dnsMs/connectMs/tlsMs/firstByteMs` 是从请求开始到阶段完成的累计时间戳，不是各阶段增量。在 `web/` 目录另运行 `node scripts/measure-public-navigation.mjs --runs 5 --output <本地 JSON 路径>`（已安装系统 Chrome 而非对应 Playwright Chromium 时加 `--system-chrome`），并用 DevTools 录制冷缓存/热缓存的首页和 `/market`、`/services` 跳转瀑布图。JSON/CSV 留在运行机器，不提交到仓库。浏览器脚本的热缓存指同一上下文返回已访问路由，不是新上下文；对照时浏览器版本、网络和缓存策略必须一致。
2. 在生产机**只读**对照本机后端 `127.0.0.1:8089/public/site-config`、`/public/models/summary` 以及本机 Nginx HTTPS 入口；观察 `ss -s`、网卡丢包/错误、Nginx 与主机商的网络监控。仅比较匿名公开请求，日志若需查看须先脱敏，不输出 URL 查询中的凭据。
3. 若受影响地区超时而正常地区和服务器本机保持正常，请相关运营商与主机商一起核对入站 SYN、重传、丢包、防火墙规则和跨运营商路由；必要时由有权限的运维人员评估更可靠的入口线路或边缘 CDN。静态 `/assets/` 可按现有不可变缓存策略缓存，HTML 不应长期缓存；鉴权 API、支付回调不能当作公开静态内容缓存。变更 DNS/代理前核对 OAuth 回调、CORS、真实客户端 IP 和支付回调，并制定回退步骤。
4. 只有在跨网络测试显示连接稳定、但 API 本机持续慢时，才按接口分析查询；只有请求已快而主线程长时间阻塞时，才优化本地化 DOM 遍历或模块重复请求。若确认冷启动资源瀑布是独立瓶颈，可另行评估 HTTP/2 和构建分包；仓库中的 Nginx 示例配置不会由现有应用发布自动生效。
