# 线上同步与并发压测执行方案

本文将“钱包充值/流水/发票权限”改造后的发布与压测动作落到可执行步骤：先按现有生产发布链路上线，再按读写比例做 k6 联合压测，输出稳定并发上限。

## 0) 目标

1. 代码按现网流程发布到生产（CI/脚本）。
2. 上线后完成烟雾与功能回归核验。
3. 做 70% 钱包分页 + 30% 下单的联合压测，并补充只读/只写场景。
4. 以“第一个不满足阈值前的最高阶段”为“可接受最大并发”。

## 1) 生产同步（按现有流程）

### 1.1 CI 路线（推荐）

1. 确认 `master` 干净且与 `origin/master` 一致。
2. 将功能提交合并到 `master`。
3. 推送到 `master`，触发 `.github/workflows/ci.yml`：
   - 后端 `verify`
   - 前端 `npm test` + `npm run build`
   - 制品打包上传并触发生产部署动作（若 secrets/环境可用）
4. 确认 CI 步骤 `deploy` 完成。

### 1.2 本地发布路线（备选）

在配置好 `api-transit-deploy` SSH Key 和 production hosts 的前提下，执行：

```powershell
.\deploy\deploy-production.ps1
```

脚本内置检查包括：

- 工作区干净
- 当前分支为 `master`
- `origin/master` 一致
- 后端与前端验证构建通过

### 1.3 发布后 Smoke（必须）

- `https://linknux.com/` 可达
- `GET https://api.linknux.com/platform/user/wallet?page=1&pageSize=10`
  返回包含 `transactionTotal/transactionPage/transactionPageSize`。
- `GET https://api.linknux.com/platform/user/recharge-orders`
  返回订单列表（至少结构正常）
- `POST https://api.linknux.com/platform/user/recharge-orders`（自定义金额 > 0）
  可成功创建订单，且返回订单编号（`id` 或 `orderNo`）

> 注意：压测及上线验证阶段暂不触发支付回调链路，只验证订单创建与查询链路即可。

## 2) 上线前/上线后功能验证样例（可直接复用）

> 前置：先让测试账号 `invoiceEnabled=true`（管理员在用户管理里开放），再验证；验证后可切回禁用。

### 2.1 充值订单接口

- 自定义金额 `customAmount > 0`：应创建成功（`planId=0`，`planName` 约定为 `自定义充值`）
- `customAmount <= 0`：应返回 400（`greater than 0`）
- `needInvoice=true` 且用户无权限：应返回 403
- `needInvoice=true` 且用户有权限：应创建成功，`invoiceRequested=true`

### 2.2 钱包流水分页

- `page=1,pageSize=10/20/50/100` 应返回完整分页元数据与对应页码数据量。
- 非法 `pageSize`（如 `7`）应回退到 `10` 并返回 fallback 后的分页结果。
- 切页不应改变 `transactionTotal`（总量字段只随实际记录变化而变）。

## 3) k6 压测脚本与执行

- 压测脚本：`scripts/k6/wallet-load.js`
- 运行封装：`scripts/k6/run-wallet-load.ps1`
- 测试账号池样例：`scripts/k6/user-token-pool.sample.csv`
- 实际账号池：复制样例为 `scripts/k6/user-token-pool.csv` 后填入；该文件已被 Git 忽略，避免 token 误提交。

### 3.1 默认场景配置（按需求）

- 默认比例：70% 读 / 30% 写（`WRITE_RATIO=0.3`）
- 默认压测段：2m @20, 2m @50, 2m @100, 2m @200, 2m @400, 2m @800（每段独立统计阈值）
- 默认阈值：
  - `http_req_failed < 1%`
  - `p95 < 1200ms`
  - `p99 < 3000ms`
  - `server_error_rate` 与 `timeout_rate` 趋近 0（无持续性 5xx/超时）

### 3.2 运行命令

```powershell
# 创建本地凭证文件（不要提交）
Copy-Item .\scripts\k6\user-token-pool.sample.csv .\scripts\k6\user-token-pool.csv

# 混合场景（默认：70%读、30%写）
.\scripts\k6\run-wallet-load.ps1 `
  -Mode mixed `
  -BaseUrl "https://api.linknux.com" `
  -UserDataFile ".\scripts\k6\user-token-pool.csv" `
  -WriteRatio 0.3 `
  -CustomAmount 12.34 `
  -PaymentMethod "alipay" `
  -SummaryOut ".\scripts\k6\wallet-load-mixed.json"

# 只读场景
.\scripts\k6\run-wallet-load.ps1 -Mode read -SummaryOut ".\scripts\k6\wallet-load-read.json"

# 只写场景（仅充值下单）
.\scripts\k6\run-wallet-load.ps1 -Mode write -WriteRatio 1 -SummaryOut ".\scripts\k6\wallet-load-write.json"
```

### 3.3 运行结果判定（“最多并发”）

按阶段产出记录：

- 每阶段 QPS/吞吐/失败率、p95/p99
- 服务端 5xx 数、超时率
- 请求日志对应的数据库连接池等待、慢查询比例

“可接受最大并发”定义为：**第一个不满足阈值前的最高阶段**。

完整 800 VU 阶段默认要求 800 个独立 token；如果只有 100~200 个账号，请先用 `-StagePlanJson` 运行到对应并发。仅做探索、接受账号复用造成的数据偏差时，才使用 `-AllowTokenReuse`。

异常归因：

- 若读场景先失效：优先查数据库索引、分页扫描计划、慢查询；
- 若写场景先失效：优先查 Hikari 连接池上限、订单创建事务耗时、相关 SQL 慢查询。

## 4) 并发容量前置假设

- 当前默认 DB 连接池上限按 `DB_POOL_MAX_SIZE=20` 计算，写场景上限通常受其约束；
- 若压测目标远高于当前稳定值，先调整连接池与数据库关键参数，再复测。
