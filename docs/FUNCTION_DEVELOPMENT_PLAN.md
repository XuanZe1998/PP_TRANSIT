# API Transit Station 功能开发计划书

> 版本：v1.0  
> 编制日期：2026-08-17  
> 规划周期：16 周  
> 适用阶段：受控内测 → 企业级可用版本  
> 默认团队规模：5–7 人

## 1. 项目概述

API Transit Station 是面向企业和开发者的多供应商大模型统一接入平台。系统通过 OpenAI 兼容接口提供模型调用能力，并统一管理渠道、模型映射、API Key、流量路由、用量结算、钱包、订单、审计及运营后台。

本计划的核心目标不是单纯增加页面或接口，而是把现有系统从“功能较完整的单体应用”升级为“边界清晰、可观测、可扩展、具备商用基础的企业级平台”。

## 2. 建设目标

### 2.1 业务目标

1. 为企业用户提供稳定、统一、可审计的大模型 API 接入服务。
2. 支持多供应商、多渠道和多价格来源，降低单一供应商故障与价格波动风险。
3. 建立从模型调用、费用预估、额度预留到实际结算的完整商业闭环。
4. 提供组织、项目、成员、权限、预算和成本中心等企业能力。
5. 将成品服务、支付、履约和创作任务建设为可独立演进的外围业务域。

### 2.2 技术目标

- 核心调用链可用性目标：不低于 99.9%。
- 网关自身新增延迟目标：P95 不高于 100 ms，不包含上游模型耗时。
- 支付、充值、订单结算不得发生重复入账或重复扣款。
- 所有模型调用、支付和管理员敏感操作均可通过请求 ID 追踪。
- 生产数据库变更全部通过版本化迁移执行，不再依赖运行期动态修表。
- 核心业务服务具备单元测试、集成测试、契约测试和故障场景测试。

## 3. 建设原则

### 3.1 核心链路优先

模型调用主链只承担鉴权、限流、路由、上游适配、响应转换、结算和审计。支付、订单履约、创作任务、通知等非实时业务不得阻塞模型调用链。

### 3.2 领域边界清晰

系统按以下业务域组织代码和数据边界：

- 身份与租户域：用户、组织、项目、成员、角色、SSO。
- 网关域：API Key、模型目录、渠道、路由、限流、协议适配。
- 计费域：价格版本、额度预留、用量结算、账本、账单。
- 支付域：支付意图、支付回调、充值、退款、对账。
- 商城履约域：商品、订单、优惠券、库存、交付、发票与收据。
- 创作任务域：图片/视频任务、供应商任务状态、结果存储。
- 运营治理域：审计、报表、告警、系统配置和供应商治理。

首期仍可采用模块化单体部署，但模块之间必须通过明确的应用服务、领域事件和数据访问边界协作，为后续拆分服务保留条件。

### 3.3 默认安全

- 真实支付、外部采购和生产写操作默认关闭。
- 密钥、JWT、数据库密码和支付私钥不得提供可用默认值。
- 高风险操作必须鉴权、授权、审计，并支持二次确认或双人复核。
- 所有回调、重试、充值和结算接口必须具备幂等机制。

## 4. 总体功能范围

### 4.1 模型网关

- OpenAI Chat Completions 兼容接口。
- 真正的 token 级 SSE 流式转发。
- Responses API、Embeddings API 和能力声明机制。
- 工具调用、JSON Schema、多模态消息等标准化转换。
- 多渠道优先级、权重、健康度和成本路由。
- 渠道熔断、半开探测、自动恢复和失败切换。
- 模型目录同步、能力探测和价格版本管理。

### 4.2 企业账号体系

- 组织、项目和环境隔离。
- 组织管理员、财务、开发者、审计员等 RBAC 角色。
- 项目级 API Key、模型白名单、IP 白名单和预算。
- OIDC/SAML SSO、SCIM 用户同步作为企业增强能力。

### 4.3 计费与财务

- 调用前费用预估和额度预留。
- 调用后按实际 usage、渠道成本和价格版本结算。
- 不可变账本、余额流水和管理员调账审计。
- 日/月预算、低余额告警和异常消耗检测。
- 用户、组织、项目、API Key、模型和渠道多维账单。

### 4.4 商城、支付与履约

- 商品规格、库存、优惠券和订单生命周期。
- 支付意图、支付回调验签、查询、关闭和退款。
- 自动履约与人工履约。
- 收据、发票和订单凭证。
- 支付对账、异常订单处理和补偿任务。

### 4.5 平台治理

- 全链路追踪、结构化日志、Prometheus 指标和告警。
- 供应商健康、延迟、错误率、成本与毛利看板。
- 操作审计、数据导出和安全策略管理。
- OpenAPI 文档、SDK 示例、Webhook 和沙箱环境。

## 5. 分阶段开发计划

## 阶段 0：工程基线治理（第 1–2 周）

### 目标

建立可重复构建、可自动验证、可安全继续开发的代码基线。

### 开发内容

- 将已被 Git 跟踪的 `web/node_modules` 从版本控制中移除。
- 修复 Maven Wrapper 在当前 Windows/PowerShell 路径环境下的启动问题。
- 建立后端测试、前端测试、生产构建和静态检查流水线。
- 引入 Flyway 或 Liquibase，生成现有数据库基线迁移。
- 禁止 `SchemaRepairService` 在生产环境自动变更表结构。
- 清理 JWT、数据库密码、支付模式等不安全默认配置。
- 划分 `local`、`test`、`staging`、`production` 配置策略。
- 为未提交的订单重构建立独立提交边界和回归清单。

### 交付物

- 干净且可理解的 Git 工作区。
- CI 流水线和构建说明。
- 数据库基线迁移脚本。
- 配置项及密钥清单。
- 当前功能回归报告。

### 验收条件

- 新环境可通过一条标准命令完成后端测试和前端构建。
- 全量自动化测试通过。
- 生产配置缺少必要密钥时应用必须启动失败或相关功能保持关闭。
- 数据库升级与回滚流程在测试数据库完成演练。

## 阶段 1：核心网关生产化（第 3–6 周）

### 目标

把统一模型调用链建设为稳定、可度量、可扩展的核心能力。

### 开发内容

#### 1. 请求与协议治理

- 定义统一的内部模型请求和响应协议。
- 实现 token 级 SSE 流式传输与客户端断开处理。
- 统一工具调用、错误码、usage 和 finish reason 转换。
- 建立 API 版本和兼容性策略。

#### 2. 路由治理

- 在现有优先级和权重机制上增加策略路由。
- 支持按成本、延迟、区域、能力、上下文长度和客户等级选择渠道。
- 引入熔断、半开探测、指数退避和健康检查。
- 标记不可安全重试的请求，防止重复上游消费。

#### 3. 分布式控制

- 使用 Redis 实现分布式 RPM、TPM 和并发限制。
- 将额度预留和释放设计为原子操作。
- 支持用户、组织、项目、API Key、模型和渠道多层限额。

#### 4. 可观测性

- 接入 OpenTelemetry Trace、Metrics 和 Logs。
- 建立请求 ID、路由 ID、结算 ID 的关联关系。
- 增加网关延迟、上游首字延迟、错误率、重试率和熔断状态指标。

### 验收条件

- OpenAI SDK 基础兼容测试通过。
- 流式请求可以实时输出，并可在客户端断开后终止或结算上游调用。
- 任一供应商故障时，可路由模型能够在策略允许范围内自动切换。
- 多实例部署下限流和额度预留结果一致。
- 每个请求都能定位到用户、API Key、路由、上游和结算记录。

## 阶段 2：计费、支付与订单闭环（第 7–10 周）

### 目标

完成可审计、可对账、可补偿的商业化闭环。

### 开发内容

#### 1. 计费账本

- 建立不可变资金账本，余额由账本汇总或受控快照生成。
- 保存请求时的销售价格、渠道成本、汇率和规则版本。
- 支持预估费用、预授权、实际结算、差额释放和异常冻结。
- 对管理员调账实施原因必填和完整审计。

#### 2. 支付意图

- 统一钱包充值和服务订单的支付意图模型。
- 支持幂等键、回调验签、金额匹配、状态机和重复回调处理。
- 实现支付查询、超时关闭、退款与退款查询。
- 建立支付回调原始证据留存和敏感字段脱敏策略。

#### 3. 订单和履约

- 完成商品、规格、库存、优惠券、订单和履约状态机。
- 自动履约通过任务队列执行，并支持失败重试和人工接管。
- 库存使用数据库锁或原子条件更新，防止超卖。
- PDF 收据和发票只能在满足支付状态与商户资料要求后生成。

#### 4. 可靠事件

- 采用数据库 Outbox 记录支付成功、订单已支付、履约完成等事件。
- 消费者必须幂等，并提供失败任务和人工重放入口。
- 定时任务只用于兜底扫描，不作为唯一业务触发方式。

### 验收条件

- 重复提交、重复回调、超时重试不会产生重复扣款、充值或发货。
- 支付金额、订单金额、账本金额和支付渠道记录可自动对账。
- 并发库存测试不存在超卖。
- 支付失败、履约失败和系统重启均有明确恢复路径。
- 任意账务变化均可追溯到业务单据、操作人和原始证据。

## 阶段 3：企业租户与开发者体验（第 11–13 周）

### 目标

让平台具备团队协作、权限隔离和标准化接入能力。

### 开发内容

- 增加组织、项目、环境和成员模型。
- 实施组织管理员、项目管理员、开发者、财务和审计员角色。
- API Key 归属调整为项目，并支持环境、模型、IP 和预算限制。
- 增加项目日/月预算与阈值告警。
- 提供 OpenAPI 文档、JavaScript/Python/Java SDK 示例。
- 提供请求调试器、请求 ID 查询、Webhook 配置和沙箱凭据。
- 用户账单支持按组织、项目、Key、模型和日期筛选导出。

### 验收条件

- 不同组织之间数据完全隔离。
- 成员权限变更立即生效并记录审计。
- 项目 API Key 无法访问未授权模型或超出预算。
- 新开发者可依据公开文档独立完成首次调用。

## 阶段 4：运营、合规与发布准备（第 14–16 周）

### 目标

完成受控商用发布需要的运营、可靠性和安全门禁。

### 开发内容

- 建立供应商、模型、租户、财务和毛利运营看板。
- 增加低余额、异常调用量、渠道失败、回调积压和库存不足告警。
- 进行容量压测、长稳测试、数据库故障和上游故障演练。
- 完成数据库备份恢复和灾难恢复演练。
- 建立数据保留、导出、删除和脱敏策略。
- 执行依赖扫描、密钥扫描、SAST、DAST 和权限边界测试。
- 完成服务条款、隐私政策、退款政策和供应商转售授权确认。

### 验收条件

- 达到约定的核心接口 SLO 和容量目标。
- 关键告警可在测试环境准确触发并形成处置记录。
- 备份可恢复至独立环境并通过数据一致性检查。
- 无未处理的严重或高危安全问题。
- 产品、研发、测试、运维、安全和业务负责人完成发布签字。

## 7. 首个迭代 Backlog（建议 2 周）

### Sprint 1 目标

完成可持续开发基线，并冻结订单重构的第一版数据模型。

### 任务清单

1. 清理 Git 中已跟踪的前端依赖目录。
2. 修复 Maven Wrapper，并让后端测试在中文路径环境可运行。
3. 建立后端测试、前端测试和构建流水线。
4. 为当前数据库生成 Flyway/Liquibase 基线。
5. 将运行时修表能力限制为开发环境。
6. 清理默认 JWT、数据库密码和支付启用配置。
7. 评审并冻结 `service_orders`、`payment_intents`、`wallet_recharge_orders`、账本和库存模型。
8. 为订单创建、支付回调、钱包充值和库存分配补充幂等测试。
9. 输出订单状态机、支付状态机和失败补偿说明。
10. 整理当前大规模未提交变更，按基础设施、后端订单、前端页面和文档拆分提交。

### Sprint 1 完成定义

- CI 全绿。
- 无真实密钥和可用生产默认值。
- 数据库可从空库迁移到当前版本。
- 重复订单请求和支付回调不会产生重复业务结果。
- 当前订单重构具备可评审的提交历史和回滚点。

## 9. 测试策略

### 9.1 自动化测试

- 单元测试：金额计算、价格版本、路由评分、状态机和权限策略。
- 集成测试：MySQL、Redis、数据库迁移、事务和并发库存。
- 契约测试：OpenAI 兼容接口、上游 Provider、支付服务和 Webhook。
- 端到端测试：注册、创建 Key、充值、调用模型、查看账单和服务下单。
- 安全测试：越权、重放、SSRF、注入、敏感信息泄露和回调伪造。
- 性能测试：非流式、流式、长上下文、多渠道故障和突发流量。

### 9.2 质量门禁

- 所有 P0/P1 功能必须有自动化验收用例。
- 核心计费、路由、鉴权和支付模块行覆盖率建议不低于 80%。
- 不以总体覆盖率代替关键业务分支覆盖。
- 存在高危安全问题、失败迁移或账务不一致时禁止发布。

## 10. 技术债务治理

- 明确 Spring MVC 与 WebFlux 的技术路线，避免用 `Mono` 包装阻塞 JDBC 形成伪异步。
- 将过大的 Controller 和 Service 按应用用例拆分，减少跨域依赖。
- 将支付、订单和模型网关的错误码统一为稳定的错误协议。
- 清理重复的用户/管理员接口和历史兼容路由。
- 为金额、币种、时区、状态值和外部业务编号建立统一值对象。
- 对调用日志和账本设计归档、分区和数据保留策略。
- 前端实施路由级拆包，降低 Element Plus 主包体积。

## 11. 主要风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 当前工作区改动过大 | 难以评审和回滚 | 按领域拆分提交，先建立基线和回归清单 |
| 支付和订单状态不一致 | 资金、发货和客诉风险 | 幂等、状态机、Outbox、对账与人工补偿 |
| 运行期自动修表 | 生产数据不可控 | 版本化迁移、演练和回滚方案 |
| 单机限流与任务状态 | 多实例数据不一致 | Redis、数据库原子更新和持久化队列 |
| 上游协议差异 | 兼容性和响应错误 | 内部统一协议和 Provider 契约测试 |
| 密钥与浏览器 Token | 凭据泄露风险 | KMS、轮换、HttpOnly Cookie、CSP 与审计 |
| 供应商不可用或涨价 | 服务中断、毛利下降 | 多渠道、健康路由、价格版本和告警 |
| 功能范围持续扩大 | 延期和质量下降 | 按 P0/P1/P2 分级，发布范围冻结 |

## 12. 关键决策点

以下事项需要在第 2 周前确认，否则会影响后续排期：

1. 首期服务对象是个人开发者、企业团队，还是两者兼顾。
2. 是否自建 Redis、消息队列和可观测平台，或采用云托管服务。
3. 首期真实支付渠道、商户主体、结算币种和退款规则。
4. 是否保留成品服务和自动履约能力，以及对应合规边界。
5. 网关采用 Spring MVC/虚拟线程还是全面响应式技术路线。
6. 企业版首期是否必须包含 SSO/SCIM。
7. 首期承诺兼容的 OpenAI API 范围和 Provider 清单。

## 13. 发布里程碑

| 里程碑 | 时间 | 结果 |
| --- | --- | --- |
| M0 工程基线 | 第 2 周 | 可重复构建、迁移和测试 |
| M1 网关 Beta | 第 6 周 | 流式、多渠道容灾、分布式限流可用 |
| M2 商业闭环 Beta | 第 10 周 | 计费、支付、订单、对账和履约可验证 |
| M3 企业内测版 | 第 13 周 | 组织、项目、RBAC、预算和开发者文档可用 |

## 14. 成功判定

计划完成不能只以“功能页面存在”为标准，应同时满足：

- 用户可以稳定完成注册、创建项目 Key、充值、调用模型和查看账单。
- 企业管理员能够控制成员、权限、预算、模型范围和审计记录。
- 平台可以在单一供应商故障时自动降级或切换。
- 支付、订单和钱包在重试、并发和故障恢复场景下保持一致。
- 运维人员可以通过指标、日志和 Trace 快速定位任一失败请求。
- 数据库升级、备份恢复、密钥轮换和故障处理均有经过验证的操作手册。
